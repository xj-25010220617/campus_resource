## 三、分工策略：混合制（Plan C）

### 策略说明

后端分 **基础设施（1人）+ 业务模块（3人）**。基础设施先行提供底层能力（OSS/Milvus/RAG/LLM/权限），业务模块在之上写接口。前端按 **页面板块（4人）** 各自负责独立页面目录，公共组件和脚手架由 A 先搭好。

### 冲突规避

- 后端每个人操作独立的 Django app 目录，互不重叠
- 前端每个人操作独立的 `src/views/<模块>/` 目录，互不重叠
- 唯一共享文件 `config/urls.py` 和 `src/router/index.js`，每人只加一行路由注册
- 基础设施人（甲）第一周配好 `settings.py` 全局配置，后续几乎不动

## 十三、文件存储业务逻辑

### 13.1 整体链路概览

```

 │  ① 计算文件MD5         │                         │                         │

 │                       │     ├─ 存在 → 返回        │                         │

 │                       │     │   resource_id:xxx}  │                         │

 │                       │                         │  ⑨ 文件写入OSS          │
 │                       │                         │                         │
 │  ⑩ POST /upload/      │                         │                         │
 │     callback/          │                         │                         │
 │     (oss_key, title,   │                         │                         │
 │      description,      │                         │                         │

```

### 13.2 接口详细逻辑

#### 接口①：获取上传凭证 `POST /api/knowledge/upload/sts/`

```
入参：
  file_name: "软件工程导论.pdf"
  file_size: 2048000
  md5: "d41d8cd98f00b204e9800998ecf8427e"

后端处理流程：
  1. 权限校验：request.user.role in ['admin', 'super_admin']
  2. MD5 去重查询：
     SELECT id FROM knowledge_doc WHERE md5_hash = md5_input LIMIT 1
     ├─ 命中 → 直接返回 {duplicate: true, resource_id: doc.id}
     └─ 未命中 → 继续
  3. 调用 OSS STS SDK：
     - RoleArn: acs:ram::xxx:role/campus-kb-upload-role
     - RoleSessionName: user_{user_id}
     - DurationSeconds: 3600
     - Policy: 仅允许 PutObject 到 knowledge/{college_id}/ 前缀
  4. 生成 oss_key：
     knowledge/{college_id}/{YYYY-MM}/{uuid}.{ext}
     示例：knowledge/3/2026-07/a1b2c3d4.pdf
  5. 生成签名上传URL（有效期300秒）
  6. 返回：
     {
       oss_key: "knowledge/3/2026-07/a1b2c3d4.pdf",
       upload_url: "https://bucket.oss-cn-hangzhou.aliyuncs.com/...?Expires=...&Signature=...",
       sts_credentials: {
         AccessKeyId: "STS.xxx",
         SecretAccessKey: "xxx",
         SecurityToken: "xxx"
       },
       duplicate: false
     }

安全要点：
  - STS Policy 限定了上传路径前缀，用户无法覆盖其他文件
  - 上传URL 300秒过期，防止泄漏后滥用
```

#### 接口②：上传完成回调 `POST /api/knowledge/upload/callback/`

```
入参：
  oss_key: "knowledge/3/2026-07/a1b2c3d4.pdf"
  title: "软件工程导论"
  description: "计算机学院软件工程专业入门教材，覆盖SDLC全流程"
  file_name: "软件工程导论.pdf"
  file_size: 2048000
  file_type: "pdf"
  md5: "d41d8cd98f00b204e9800998ecf8427e"
  discipline_id: 5
  category_id: 12
  college_id: 3 (可选，默认取上传者college_id)

后端处理流程：
  1. 权限校验
  2. 校验 oss_key 格式合法性（防止路径穿越）
  3. 再次 MD5 去重（防止并发上传导致重复）—— 数据库唯一约束兜底
  4. INSERT INTO knowledge_doc:
     - uploader_id = request.user.id
     - status = 'uploaded'
     - 其他字段直接写入
  5. 调用 Celery 异步任务：
     index_document.delay(doc_id=new_doc.id)
  6. 返回 {id: new_doc.id, status: 'uploaded'}
```

#### 接口③：Celery 异步索引任务

```
index_document(doc_id):
  1. 从 MySQL 读取 knowledge_doc 记录
  2. 状态更新为 'processing'
  3. 用 OSS SDK 下载文件到临时目录
  4. 根据 file_type 选择解析器：
     ├─ pdf  → PyMuPDF / pdfplumber
     ├─ doc  → python-docx
     ├─ ppt  → python-pptx
     ├─ xls  → openpyxl
     ├─ md/txt/html → 直接读取
     ├─ image → OCR（pytesseract）或仅保留标题+描述
     ├─ video/audio → 仅保留标题+描述为可检索文本
     └─ other → 同上
  5. 文本分块（semantic chunking）：
     - 优先按段落/标题自然边界切分
     - 每块最大 512 tokens
     - 相邻块重叠 128 tokens
     - 每块记录 page_number（对PDF）
  6. 批量 Embedding：
     - 调用 text-embedding-v3 或同级别模型
     - 每批 20 个 chunk，并发请求
  7. 批量写入 Milvus：
     - Collection: knowledge_chunks
     - Fields: chunk_id, doc_id, chunk_text, vector(1536维), page_number, seq_order
  8. 更新 doc 状态：
     UPDATE knowledge_doc
     SET status = 'indexed',
         chunk_count = {分块数},
         indexed_at = NOW()
     WHERE id = doc_id

异常处理：
  - 解析失败 → status = 'error', 记录异常信息
  - Embedding API 超时 → 重试3次，每次间隔 2^n 秒
  - Milvus 写入失败 → 重试，最终失败则 status = 'error'
```

### 13.3 文件下载签名 URL

```
POST /api/knowledge/docs/{id}/download/

后端处理流程：
  1. 权限校验：admin 只能下载自己上传的文档
  2. 查 knowledge_doc 获取 oss_key
  3. 调 OSS SDK 生成签名下载 URL（有效期300秒）
  4. 返回 {download_url: "https://..."}
  或 HTTP 302 重定向

为什么用签名URL而不是直接代理文件流：
  - 文件可能很大（>100MB），Django 代理会阻塞 worker
  - OSS 直接传输不占用应用服务器带宽
  - 签名 URL 防止盗链（300秒过期）
```

### 13.4 删除级联逻辑

```
DELETE /api/knowledge/docs/{id}/

后端处理流程：
  1. 权限校验
  2. 开启数据库事务
  3. 从 Milvus 删除该 doc 所有 chunk：
     milvus_collection.delete(f'doc_id == {doc_id}')
  4. 删除 OSS 文件：
     oss_client.delete_object(oss_key)
  5. 删除 MySQL 关联数据（逐级）：
     DELETE FROM knowledge_keyword WHERE doc_id = {id}
     DELETE FROM knowledge_doc_chunk WHERE doc_id = {id}
     DELETE FROM knowledge_doc WHERE id = {id}
  6. 提交事务

回滚策略：
  - Milvus 删除失败 → 事务回滚，返回 500
  - OSS 删除失败 → 记录日志，继续（非阻断）
  - MySQL 删除失败 → 事务自动回滚
```

### 14.2 各步骤详解

#### 步骤⑤：问题向量化

```
函数：embed_question(question_text) → list[float]

实现：
  1. 调用 Embedding API（与文档索引使用同一模型）
  2. 请求体：
     {
       model: "text-embedding-v3",
       input: question_text
     }
  3. 返回 1536 维向量（以 text-embedding-v3 为例）
  4. 缓存策略：完全相同的问题在 5 分钟内走本地缓存（LRU dict）

降级方案（如果 Embedding API 不可用）：
  - 直接走关键词匹配（用 MySQL LIKE + 全文索引）
  - 返回降级标记，confidence 设为 0.5
```

#### 步骤⑥：Milvus 相似检索

```
参数：
  collection: "knowledge_chunks"
  vector: embedding(1536维)
  top_k: 10
  metric_type: "COSINE"
  filter: college_id == user.college_id (可选，按学院限定范围)
  output_fields: ["chunk_text", "doc_id", "page_number", "seq_order"]

返回值：
  [
    {
      id: 12345,
      score: 0.92,
      entity: {
        chunk_text: "软件工程生命周期通常包括需求分析...",
        doc_id: 67,
        page_number: 3,
        seq_order: 2
      }
    },
    ... (最多10条)
  ]

过滤逻辑：
  - super_admin / admin：不限制学院，全局检索
  - user：默认限定本学院文档（可通过参数选择是否跨学院）
```

#### 步骤⑦：提示词组装

```
系统提示词模板：

"你是成都东软学院的AI知识助手，专门回答与学院教学、科研、管理相关的问题。
请基于以下参考资料回答问题。如果参考资料无法回答，请如实告知，不要编造。

参考资料：
---
{doc_title} (第{page}页):
{chunk_text}
---
{doc_title} (第{page}页):
{chunk_text}
---
...

指令：
1. 优先使用参考资料中的内容回答
2. 如果资料足够，请列出具体的出处（文档名+页码）
3. 如果资料不足，说明"根据现有知识库，暂时无法完整回答这个问题"
4. 回答使用中文，专业术语可附英文原文
5. 回答应结构清晰，适当使用列表或分点"

user_prompt: 用户原始问题

组装逻辑：
  - 按 score 降序排列检索结果
  - score < 0.6 的 chunks 不放入上下文（噪声）
  - 上下文总长度不超过模型context窗口的60%（留空间给回答）
  - 如果没有任何 chunk score > 0.6，走人工兜底流程
```

#### 步骤⑧⑨⑩：LLM 流式调用 + SSE 代理

```
函数：call_llm_stream(messages) → AsyncGenerator[str]

实现：
  1. 构造请求：
     POST https://api.deepseek.com/v1/chat/completions
     (或阿里云通义千问 endpoint)
     {
       model: "deepseek-chat",
       messages: [
         {role: "system", content: system_prompt},
         {role: "user", content: user_prompt}
       ],
       stream: true,
       temperature: 0.3,
       max_tokens: 2048
     }

  2. 异步迭代响应 (httpx + aiter_bytes)：
     for chunk in response.aiter_lines():
         if chunk.startswith("data: "):
             data = json.loads(chunk[6:])
             token = data["choices"][0]["delta"]["content"]
             yield token

SSE 代理层 (Django StreamingHttpResponse)：

  def ask_view(request):
      # ... 前置处理 ...
      
      async def event_stream():
          # 1. 先发 start
          yield f"event: start\ndata: {json.dumps(start_data)}\n\n"
          
          # 2. 流式转发 LLM token
          full_answer = ""
          async for token in call_llm_stream(messages):
              full_answer += token
              yield f"event: token\ndata: {json.dumps({'content': token})}\n\n"
          
          # 3. 保存完整回答
          save_message(conversation_id, 'assistant', full_answer)
          
          # 4. 发 references
          yield f"event: references\ndata: {json.dumps(ref_data)}\n\n"
          
          # 5. 发 suggested
          suggested = await generate_suggestions(question, full_answer)
          yield f"event: suggested\ndata: {json.dumps(suggested)}\n\n"
          
          # 6. 发 confidence
          yield f"event: confidence\ndata: {json.dumps({'score': calc_confidence})}\n\n"
          
          # 7. 发 done
          yield f"event: done\ndata: {json.dumps({'tokens_used': token_count})}\n\n"
      
      return StreamingHttpResponse(
          event_stream(),
          content_type='text/event-stream',
          headers={
              'Cache-Control': 'no-cache',
              'X-Accel-Buffering': 'no',  # 禁用nginx缓冲
              'Connection': 'keep-alive',
          }
      )
```

#### 步骤⑬～⑭：引用返回与权限分级

```
函数：build_references(search_results, user_role, user_id)

逻辑：
  base_refs = [
    {
      doc_title: result.entity.chunk_text 反查 knowledge_doc.title,
      doc_id: result.entity.doc_id,
      page: result.entity.page_number,
      score: result.score,
      content_snippet: result.entity.chunk_text[:200],
      download_url: generate_oss_download_url(doc.oss_key) // 仅授权用户
    }
    for result in search_results if result.score > 0.7
  ]

  if user_role == 'user':
      # 普通用户只看到计数 + 摘要
      return SSE事件:
        event: references
        data: {
          count: len(base_refs),
          summary: f"参考了{len(base_refs)}份文档"
        }

  elif user_role in ['admin', 'super_admin']:
      # admin 进一步过滤：只能看自己上传的
      if user_role == 'admin':
          base_refs = [r for r in base_refs
                       if r.doc.uploader_id == user_id]
      
      # 对每个引用生成 OSS 签名下载 URL
      for ref in base_refs:
          ref.download_url = oss_sign_url(ref.doc.oss_key, expire=300)
      
      return SSE事件:
        event: references_detail
        data: [
          {
            doc_title: "...",
            doc_id: 67,
            page: 3,
            score: 0.92,
            content_snippet: "软件工程生命周期...",
            download_url: "https://oss-cn-xxx.aliyuncs.com/...?Expires=..."
          },
          ...
        ]
```

#### 步骤⑮：推荐问题生成

```
函数：generate_suggestions(question, answer)

实现：
  1. 调用 LLM（非流式，轻量 prompt）：
     {
       model: "deepseek-chat",
       messages: [
         {role: "system", content: "你是一个问题推荐助手。基于用户的问题和AI回答，生成3个用户可能感兴趣的后续追问。"},
         {role: "user", content: f"问题：{question}\n回答：{answer[:500]}\n请生成3个追问，每个不超过30字，直接JSON数组返回。"}
       ],
       temperature: 0.7,
       max_tokens: 200,
       response_format: {type: "json_object"}
     }
  2. 解析返回的 JSON 数组
  3. 去重（与当前问题和历史问题比较）
  4. 返回最多 3 个

降级方案：
  - LLM 调用失败 → 返回通用追问模板：
    ["能详细说明一下吗？", "有哪些相关的资源可以查阅？"]
```

#### 步骤⑯：置信度计算

```
函数：calc_confidence(search_results)

算法：
  top3_scores = [r.score for r in search_results[:3]]

  if len(top3_scores) == 0:
      return 0.0

  # 加权平均：第一个权重最高（最相关）
  weights = [0.5, 0.3, 0.2]
  weighted_avg = sum(s * w for s, w in zip(top3_scores, weights))

  # 如果最高分低于 0.6，整体置信度打折
  if top3_scores[0] < 0.6:
      weighted_avg *= 0.7

  return round(weighted_avg, 2)
```

### 14.3 人工兜底触发条件

```
以下三种情况触发人工兜底：

条件1 — 检索结果太差：
  最高分 chunk score < 0.6
  
条件2 — 用户主动反馈：
  用户点踩且 reason 不为空
  → 自动创建 pending_feedback 记录

条件3 — LLM 明确表示无法回答：
  LLM 回答中包含 "暂时无法完整回答" / "现有知识库不足"
  → 自动创建 pending_feedback 记录，关联 conversation_id

人工兜底流程：
  1. INSERT INTO pending_feedback
     (question, conversation_id, college_id, status='pending')
  2. admin 在管理后台看到待回答列表
  3. admin 填写答案 → POST /api/feedback/{id}/answer/
  4. 回答文本自动作为新文档索引入库：
     - 创建 knowledge_doc (file_type='qa', source_type='manual')
     - 触发 Celery 索引任务
     - 后续相同问题可直接命中
  5. 状态更新为 'answered'
```

### 14.4 会话管理

```
Conversation 模型（已在规划中，需新建）：

  id: BIGINT PK
  user_id: FK → user
  title: VARCHAR(256)
  is_favorite: BOOL DEFAULT FALSE
  created_at: DATETIME
  updated_at: DATETIME

Message 模型（已在规划中，需新建）：

  id: BIGINT PK

  role: VARCHAR(16)  -- 'user' | 'assistant'
  content: LONGTEXT

  rating_reason: TEXT NULL

  message_references:

会话创建规则：

  - conversation_id 传入 → 校验 user_id 归属（403 if 不属于）
```

### 14.5 控制参数汇总

| 参数 | 默认值 | 说明 |
|------|:-----:|------|
| `RAG_TOP_K` | 10 | Milvus 检索返回数量 |
| `RAG_SCORE_THRESHOLD` | 0.6 | 低于此分数的 chunk 不放入上下文 |
| `RAG_REFERENCE_THRESHOLD` | 0.7 | 低于此分数的不作为引用展示 |
