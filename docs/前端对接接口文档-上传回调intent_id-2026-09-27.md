# 前端对接接口文档 —— 上传回调必须携带 intent_id（2026-09-27）

> **收件人：前端负责人**
> 本文是**待前端配合的变更说明**，不是"已完成"的通知。仓库内不含前端代码，
> 后端无法验证前端是否已改。请在发版前确认本项已落地。
>
> 涉及后端分支：`phase-1-1-security-stopgap`
> 后端权威文档：`docs/API文档.md` §4.2、`docs/Apifox接口测试指南.md` §3.2

---

## 1. 一句话结论

上传流程从"两步"变成"**三步**"：拿凭证 → 前端直传 OSS → **回调时必须带上
服务端签发的 `intent_id` 和同一个隔离区 `oss_key`**。

只带 `oss_key` 的回调现在会被拒（HTTP 400），文件不会被入库。

---

## 2. 变更前后对比

| | 变更前（旧契约） | 变更后（当前契约） |
|---|---|---|
| `POST /api/knowledge/upload/sts/` 返回 | `oss_key` 等凭证 | `oss_key`（隔离区）+ **`intent_id`（新增）** |
| 直传目标 | 任意 | **必须**是返回里的那个 `oss_key`，不能自己拼 |
| `POST /api/knowledge/upload/callback/` 必填字段 | `oss_key`、`file_name`、`file_size`、`file_type`、`md5` | 以上全部 **+ `intent_id`** |
| 服务端凭什么信任这次上传 | 只能证明对象存在 | **证明这个对象是本次凭证指定的那一个** |

**为什么要改**：旧契约只校验"OSS 里存在这个 key、大小对得上"，任何人只要
猜到/拿到一个路径就能把它注册成自己的文档。`intent_id` 是服务端签发的凭证，
把「谁上传的」和「对象具体是哪一个」绑在一起。

---

## 3. 前端需要改的代码（伪代码）

```js
// ① 申请凭证
const sts = await api.post('/api/knowledge/upload/sts/', {
  file_name: file.name,
  file_size: file.size,
  file_type: ext,
  md5: md5,
});
// sts.data = { intent_id, oss_key, quarantine_key, status, expires_at, ... }

const { intent_id, oss_key } = sts.data;

// ② 直传 OSS —— 目标 key 必须原样用 oss_key，不要自己拼路径
await ossClient.put(oss_key, file);

// ③ 回调 —— 必须带上 intent_id，且 oss_key 与 ① 返回的**完全一致**
await api.post('/api/knowledge/upload/callback/', {
  intent_id,                       // ← 新增，必填（整数）
  oss_key,                         // ← 与 ① 完全一致，不能拼接、不能改名
  file_name: file.name,
  file_size: file.size,
  file_type: ext,
  md5: md5,
  title: file.name,                // 可选
  // scope / category_id 已废弃，传了也不生效，建议删除
});
```

**`intent_id` 是整数**（示例 `37`），不是字符串、不是 UUID。它是 `/sts/` 响应
里的字段名就叫 `intent_id`。

## 4. 服务端会做的 5 项校验（对应错误响应）

| # | 校验 | 不通过时 |
|---|---|---|
| 1 | `intent_id` 存在、属于**当前登录用户**、未过期、状态可用 | 404 `intent 不存在或不属于当前用户` / 409 状态冲突 |
| 2 | `oss_key` 与 intent 记录的隔离区 key **精确相等** | 400 `OSS Key 与上传凭证记录的目标对象不一致` |
| 3 | 该对象真实存在、大小与声明一致（以 OSS `head_object` 为准）、类型合规、ETag 与 md5 一致 | 400 |
| 4 | 意图原子置为已消费（CAS 防重放） | 409 |
| 5 | `oss_key` / `md5` 重复 → 返回 `duplicate: true`，且**他人不可见** | 400 |

常见前端问题自查：

- **400 且提示缺 `intent_id`** → 回调没带这个字段（最常见）。
- **400 且提示 key 不一致** → 直传时自己拼了路径，或回调传的 key 和 ① 返回的不一致。
- **404 intent 不存在或不属于当前用户** → `intent_id` 存错（比如串了用户/页面刷新后丢了），或凭证已过期，需重新走 ① 申请。**注意：`/sts/` 返回 `duplicate: true` 时不会签发 intent，此时不要调回调。**

---

## 5. 一个容易踩的点：token 过期

`intent_id` 有有效期（见 ① 响应里的 `expires_at`）。用户选完文件、慢慢等上传
完成后才回调，可能已过期。建议：**① 的调用尽量贴近 ② 的直传动作**，不要在
页面加载时就把 intent 申请好。

---

## 6. 联调自测清单

- [ ] 正常上传：拿到 `intent_id` → 直传 → 回调 200，文档出现在列表（状态为待审核）
- [ ] 回调故意不带 `intent_id` → 400，且列表里不出现文档
- [ ] 回调用别人的 `intent_id` → 404
- [ ] 回调传一个自己改过的 `oss_key` → 400
- [ ] 上传同名同内容的文件 → 第二次返回 `duplicate`，不产生重复文档

> 上传成功的文件会先进入**隔离区**（`quarantine/…`），经后台内容审核通过后才会
> 被提升为正式文件并对外可检索。因此**刚上传完在问答里搜不到是正常的**，不是 bug。
