# 生产部署编排说明（P1-2 Phase 1-2 / 审计报告 P-5、P-6）

> 背景：STEP 4-B 的审核 → 提升 → 索引链路依赖 Celery 异步执行，但仓库里
> **没有任何 worker / beat 启动脚本**，生产入口还是 `manage.py runserver`。
> 本地开发因为 `shared_task_compat` 会把 `task.delay()` 降级成就地同步执行，
> 完全掩盖了这个问题——直到上生产才暴露。
>
> 本文档是 P1-2 Phase 1-2 交付的部署编排说明。

---

## 一、进程编排：三个进程，缺一不可

| 进程 | 脚本 | 作用 | 不具备时的后果 |
|------|------|------|----------------|
| Web | `backend/deploy/start_web.bat` | 对外 HTTP 服务 | 服务不可用 |
| Worker | `backend/deploy/start_worker.bat` | 消费审核 / 提升 / 索引任务 | **上传的文档永久停在"已上传未审核"**，知识库停止增长 |
| Beat | `backend/deploy/start_beat.bat` | 定时调度（含审核失败重试 + 未入队补扫） | 审核失败的文档不再重试；broker 抖动期间丢失的上传无人补扫 |

⚠️ **Worker 与 Beat 必须是两个独立进程**。不要用 `celery -B` 单进程同时跑
两者：多 worker 场景下会重复调度。

### 1.1 环境变量

| 变量 | 默认 | 说明 |
|------|------|------|
| `CAMPUS_PORT` | `8000` | Web 监听端口。**必须与 `deploy/nginx.conf` 的 upstream 一致** |
| `CELERY_POOL` | `solo` | Windows 不支持 prefork；Linux 可设 `prefork` |
| `CELERY_CONCURRENCY` | `4` | worker 并发 |
| `CAMPUS_BACKEND_DIR` | 脚本所在目录 | 后端目录，覆盖默认推断（避免写死某台机器的绝对路径） |

### 1.2 端口统一

改造前仓库内**不一致**：`deploy/nginx.conf` 指向 `127.0.0.1:8000`，
而 `start.bat` 监听 `0.0.0.0:3000`。本阶段统一为 **8000**。

> **PRODUCTION_PORT_NOT_VERIFIED**：开发机无法访问生产环境，生产实际监听
> 端口未能确认。上线前请核对，如需变更请**同时**修改：
> `deploy/nginx.conf` 的 `upstream django` 与 `deploy/start_web.bat` 的 `CAMPUS_PORT`。

`backend/start.bat` 保留 3000 端口，是**刻意**的：它已被降级为本地开发专用
（见下节），与生产端口无关。

### 1.3 🚫 BLOCKED：生产 WSGI 依赖未决

改造前生产用 `manage.py runserver`。那是 Django 的**开发**服务器——单进程、
无并发保护、官方明确声明不得用于生产。

本阶段**没有**擅自引入新依赖（约束：不新增依赖）。`deploy/start_web.bat`
的行为是：

1. 依次探测 `waitress`（Windows 推荐）与 `gunicorn`（Linux）；
2. 都不可用 → **退出码 2**，打印 `BLOCKED: production WSGI dependency/plan required`；
3. **绝不回退到 `runserver`**。

补齐路径（任选其一，脚本无需修改即可生效）：

```bash
# 方案 A：Windows（waitress 支持 Windows，gunicorn 不支持）
echo "waitress>=3.0.0" >> backend/requirements.txt
backend/venv/Scripts/pip.exe install "waitress>=3.0.0"

# 方案 B：改用 Linux 部署
echo "gunicorn>=21.2.0" >> backend/requirements.txt
pip install "gunicorn>=21.2.0"
```

在补齐之前，生产 Web 服务处于 **未就绪** 状态——这是刻意的（让问题暴露，
而不是被 runserver 掩盖）。

## 二、生产环境变量（P-6）

`backend/config/settings.py` 现在**缺省即安全 + 配错就拒绝启动**。生产环境
必须显式设置下列变量（写在 `.env` 里，`.env` 不入库）：

| 变量 | 生产要求 | 配错的后果 |
|------|----------|------------|
| `DJANGO_DEBUG` | `false`（默认即为 false） | `true` 会让 `CORS_ALLOW_ALL_ORIGINS` 默认为 true |
| `SECRET_KEY` | 必须显式设置，且不能等于开发默认密钥 | 使用默认密钥 → **拒绝启动** |
| `DJANGO_ALLOWED_HOSTS` | 显式列出真实域名，逗号分隔，**禁止 `*`** | 缺失或含 `*` → **拒绝启动** |
| `CORS_ALLOW_ALL_ORIGINS` | `false` | `true` → **拒绝启动** |
| `CORS_ALLOWED_ORIGINS` | 显式列出前端源，例如 `https://example.edu.cn` | 缺失时为空列表（跨域全部拒绝，fail-closed） |

示例（**请勿把真实域名与密钥提交到仓库**）：

```dotenv
DJANGO_DEBUG=false
SECRET_KEY=<生产随机密钥>
DJANGO_ALLOWED_HOSTS=example.edu.cn,www.example.edu.cn
CORS_ALLOW_ALL_ORIGINS=false
CORS_ALLOWED_ORIGINS=https://example.edu.cn
```

**兼容性**：旧的 `DEBUG` / `ALLOWED_HOSTS` / `CORS_ORIGINS` 变量名依然被识别
（`DJANGO_*` 优先），已有 `.env` 不会直接失效。但旧的 `ALLOWED_HOSTS=*`
在生产（`DEBUG=false`）下会**导致启动失败**——这正是本次要修的问题，请按上表
改为显式域名。

**本地开发不受影响**：`DEBUG=true` 时 `ALLOWED_HOSTS=*` 与
`CORS_ALLOWED_ORIGINS=http://localhost:5173` 的兜底照旧。

## 三、审核未通过内容的处置

上传链路已与审核链解耦（P-4）：HTTP 请求只负责"落盘 + 建文档 + 入队"，
**绝不**同步跑审核 → 提升 → 索引。队列不可用时文档保持未审核、对象留在
`quarantine/`，由 beat 的 `retry-failed-moderations`（每 10 分钟）补扫重派。

### 3.1 查看卡住的文档

```bash
cd backend
venv\Scripts\python.exe manage.py confirm_moderation --list
```

### 3.2 人工确认放行（仅在确有必要时）

只允许对 `state=unavailable`（检测链没能给出结论）的文档执行；`rejected`
永远不能翻案；对象必须真实存在于 `quarantine/`。确认后仍走 promotion →
`knowledge/` → index，**不绕过提升**。

```bash
venv\Scripts\python.exe manage.py confirm_moderation ^
    --doc-id 123 --actor <管理员用户名> --reason "<复核依据>"
```

也可通过 Django Admin（`/admin/` → 内容安全审核 → 选中记录 → "人工确认放行"），
两个入口共用同一条 service，写入的审计字段一致（`confirmed_by` /
`confirmed_at` / `confirmation_reason`）。

## 四、重索引

`scripts/reindex_all.bat` 已重写为 `manage.py reindex_docs` 的薄封装。三条
破坏性操作（清空全部 `DocChunk`、批量重置 `KnowledgeDoc.status`、
`rmdir chroma_db`）**已全部删除**。

```bash
# 1) 先看统计，不产生任何写入
scripts\reindex_all.bat --dry-run

# 2) 预检通过后再重建（存在任一不可索引文档时整体退出，不做任何写入）
scripts\reindex_all.bat

# 3) 连已 indexed 的也重建（仍然逐条过审核门）
scripts\reindex_all.bat --force --limit 50
```

> ⚠️ 当前生产库有 95 份**无 `ContentModeration` 记录**的历史文档，它们会被
> 判定为"不可索引"。因此第 2 步会**直接退出**——这是设计如此（fail-closed），
> 不是故障。历史数据的处理属于独立阶段（审计报告 P-8），本阶段不做回填。
