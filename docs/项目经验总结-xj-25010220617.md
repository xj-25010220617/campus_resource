## 一、奠基阶段（06-30 ~ 07-01）

### 1.1 无设计不编码

**问题**：团队 5 人并行开发，接口口径、表结构、职责边界没有共识，直接开写必然冲突。

**解决**：
- `8b7a8e5` 先写《团队分工与四周排期设计》，把人/模块/时间盒定死；
- `4538661` 补充文件存储与智能问答的**详细业务逻辑**（STS 凭证、MD5 去重、回调创建、文本直传全链路）；
- `b70a325` 沉淀 `CONVENTIONS.md`（152 行）+ `campus_resource.sql` 初始库结构，让规范可引用、建库可复现。

**学到什么**：多人项目里，`CONVENTIONS.md` + 初始 SQL 这类"可执行规范"比口头约定有效得多。后面两个月队友的提交（权限类、日志模块）都是在这个骨架上长出来的。

### 1.2 基础设施一次到位（`416ea7e`，+1007 行）

**问题**：问答要同时依赖 Celery 异步任务、LLM 调用、向量库、OSS 存储、SSE 流式输出，任何一处裸写都会散落各处难维护。

**解决**：
- `config/celery.py`（312 行）：beat 调度、任务路由集中管理；
- `utils/llm.py`：LLM 与 Embedding 客户端统一封装；
- `utils/milvus.py`：Milvus/Chroma 双后端（生产 Milvus 不可用时降级本地 Chroma）；
- `utils/oss.py`、`utils/sse.py`、`utils/rag.py` 骨架。

**踩的坑**：这次提交把 `__pycache__/*.pyc` 二进制文件一起提交进了仓库——基础设施提交动了十几个文件，没检查暂存区。

**学到什么**：① 大提交前必须 `git status` 逐文件过一遍，或配好 `.gitignore`（本仓库后来才由队友补上）；② 降级双后端（Milvus→Chroma）从第一天就写进架构，后来证明是开发环境能持续跑下去的关键。

## 二、FAQ 系统：从零到一（07-03 ~ 07-10）

### 2.1 权限先行（`c089a4c` → `a24423b`）

**问题**：FAQ 谁能建、谁能审、谁能看？没有权限类，views 写出来就是裸奔。

**解决**：先建三张表（`FAQCategory`/`FAQItem`/`FAQGenerationLog`），随后第一件事就是 `IsCollegeAdmin`/`IsFAQAdmin` 权限类 + Django Admin 注册，然后才写 serializers/views/urls（`5d1108e`，206 行 views）。

**学到什么**："模型 → 权限 → 接口 → 任务"的顺序比"先跑通再说"省一次返工。这个顺序后来在 `ae6b1d1`（完整实现，+2519 行）里兑现：FAQ 自动生成管线（tasks.py 195 行）+ 提问时 FAQ 短路（短问题优先查 FAQ 表，命中直接返回不打扰 LLM）。

### 2.2 冷启动没有数据（`ed24afd`、`1f1b72f`）

**问题**：FAQ 表是空的，短路逻辑永远不命中，演示时 FAQ 模块形同虚设；人工录入 50 条成本太高。

**解决**：
- `ed24afd`：`seed_faq.py` 管理命令（552 行）灌入种子数据；
- `1f1b72f`：`generate_faq_from_website` 命令——把爬虫抓到的官网通知/公告喂给 LLM 自动生成 FAQ 条目，生成结果落 `FAQGenerationLog` 可追溯。

**学到什么**：AI 项目演示的死穴是"没有数据"。让爬虫（数据源）→ LLM（生成）→ FAQ 表（消费）形成自动闭环，比人工灌数据可持续。

## 三、爬虫与智能体（07-06 ~ 07-10）

### 3.1 官网爬虫的工程化（`c0ef50a`、`eec4ba3`、`11856e7`、`981d3c3`）

**问题**：知识库只有用户手动上传的文件，覆盖不了"通知公告/校园时讯/招生就业"这类官网信息；直接爬又有三个坑——重复爬、被封、内容残缺。

**解决**（`utils/crawler.py` 的 `NeusoftSpider`）：
- BFS 广度优先 + 自动发现 16 个重要栏目；
- **双重去重**：URL 去重 + 内容 MD5 去重（同一页面改版重发不会重复入库）；
- 请求间隔控制防封禁；
- 爬取结果直接落 `KnowledgeDoc(source_type='website')` 并自动触发异步索引；
- `eec4ba3` 把调度交给 Windows 计划任务（`crawl_daily.bat` + `crawl_weekly.xml`：每天 04:00 增量 100 页、每周日 05:00 全量 300 页），Celery beat 负责应用内定时，两条腿走路。

**学到什么**：爬虫 80% 的工作量在"不重复 + 不被封 + 自动调度"，真正的抓取逻辑只占 20%。

### 3.2 提问意图路由（`c0ef50a`）

**问题**：用户问"我传过几个文件""最近上传了什么"这类**文件管理查询**时，走 RAG 向量检索完全是答非所问——答案在数据库里，不在文档正文里。

**解决**：`utils/query_router.py` 规则匹配 5 类意图（文档数统计/最近上传/存储统计/分类分布/条件查找），命中后走 `data_query.py` 直查数据库再让 LLM 格式化；在 AskView 的敏感检查之后、RAG 之前插入路由。

**学到什么**：LLM 应用第一层不是模型而是**分流**——什么问题该查库、什么问题该检索、什么问题该联网，路由错了一切白费。

### 3.3 联网兜底三级降级（`6e29dbf`）

**问题**：内建知识库覆盖不了的问题（如"今年招生政策"），LLM 只能凭训练数据瞎编。

**解决**：`web_fetcher.py` + `web_search.py` 建立三级 fallback：requests+BeautifulSoup → Playwright JS 渲染 → baidusearch 补充；知识库无结果时自动联网搜索，结果作为 system prompt 注入 LLM。配套踩坑：JS 渲染页面用 requests 拿不到正文（所以必须 Playwright 这一级）；baidusearch 过度使用会触发 IP 封锁（所以调用间隔 15 秒）。

**学到什么**：外部依赖（反爬、IP 封锁、JS 渲染）不可控，fallback 链 + 间隔控制是"能一直用"和"偶尔能用"的区别。

### 3.4 502 网关超时的系统性治理（`5b32909`、`964949b`）⭐ 本阶段最有价值

**问题**：生产环境流式问答频繁 502。表面看是"服务器不行"，实际是**整条调用链的超时预算失控**：LLM 流式响应 60~190 秒，而 nginx 默认 proxy_read_timeout 60 秒——后端还在生成，网关已经断了。且当时所有外部调用共用一个 `connect_timeout=5` 单值超时（同时限制连接和读取，读 LLM 长响应必然超时）。

**解决**：
- `964949b`：`connect_timeout=5` → `(5, 60)` 元组，连接与读取分离；
- `5b32909`：新建 `utils/http_client.py`——**按服务分档的超时档案**（llm_chat 10/60、llm_stream 10/60、llm_vision 10/120、aliyun_embed 10/30、oss_download 5/120），全部外部调用统一走档案注入；**熔断器**（连续 5 次失败后 60 秒内快速失败，不再雪崩堆积）；**nginx 配套**（`deploy/nginx.conf`：`/api/chat/` 的 proxy_read_timeout 提到 300s，并刻意让 LLM 重试总预算 3×60+退避≈190s 落在 300s 之内，保证超时 error 事件发得出去）；`config/middleware.py` 兜底。
- `3421042`：趁势统一错误码（`utils/error_codes.py`），accounts/chat/knowledge/sse 四处接入，前端不再解析五花八门的错误格式。

**学到什么**：⭐ 网关超时从来不是单点问题。修复公式 = **下游超时档案 × 重试预算 × 网关 read_timeout** 三者对齐。只改任何一处都会复发。熔断是把"上游拖死"变成"快速失败"的保险丝。

## 四、检索架构演进（09-01 ~ 09-03）

### 4.1 Query 改写：口语化提问 → 可检索查询（`d187e00`）

**问题**：用户问"食堂饭卡丢了咋办"，直搜向量库命中率低——用户口语和文档措辞差异太大；另外短问题明明 FAQ 表里有现成答案，也去跑了一遍昂贵的 LLM+检索全流程。

**解决**：
- 新建 `utils/query_rewriter.py`：规则改写（零成本，覆盖高频模式）+ LLM 改写（兜底），结果进 Django 缓存避免重复改写；
- 多版本检索：改写出的多个查询变体都检索一遍再合并去重；
- 参数重调：`RAG_TOP_K 10→15`（召回更多候选交给精排）、`SCORE 0.35→0.30`（配合 Rerank 兜住低分真相关）、`REFERENCE 0.7→0.65`；
- Rerank 触发放宽：`CROSS_ENCODER_MIN_TRIGGER=3`，候选 ≥3 即精排，不再等攒够一批；
- 新增检索质量监控日志（每问记录各通道命中数），为后续 `c36971b`/`b754139` 的排查埋了伏笔；
- FAQ 短路收口进 chat 视图。

**学到什么**：⭐ 检索质量 = 召回（TOP_K/多版本）→ 精排（Rerank）→ 过滤（阈值）三级联调，单独调任何一级都会按下葫芦浮起瓢。且**监控日志要和功能一起上线**——两个月后定位向量通道 0 命中，靠的就是这批日志。

### 4.2 LLM 幻觉日期（`0d4b113`）⭐ AI 应用经典坑

**问题**：用户问"今天的通知有哪些""今年毕业政策"，LLM 用训练数据里的旧日期一本正经地编造"今天"的答案。

**解决**：新建 `utils/context.py`（83 行）`build_system_context()`——所有 LLM 调用的 Prompt 头部统一实时注入当前时间；Celery beat 每天 00:05 刷新上下文缓存；敏感词检查、RAG、data_query、FAQ 全路径接入。

**学到什么**：⭐ 任何时间敏感的 LLM 调用必须注入系统时间，这是硬规则——LLM 的"今天"永远是它训练截止的那天。注入点要收敛到一个函数（context.py），而不是各调用点自己拼。

### 4.3 双表归一：859 行的技术债偿还（`59e08f8`）

**问题**：早期建模时 `resources.Resource` 和 `knowledge.KnowledgeDoc` 双表并存，同一份文件数据两处存放。后果是 query_router、data_query、rag 三个模块到处写 `if 用 A 表 else 用 B 表` 的适配代码，每加一个功能都要双份维护，还出过两边数据不一致。

**解决**：`0009_remove_legacy_resource_models` 迁移退役旧表，`data_query.py`（207 行变化）、`query_router.py`、`rag.py`（-331 行）全部改写为只认 `KnowledgeDoc`，admin_panel 权限同步收敛。净删 561 行。

**学到什么**：⭐ "先并存、以后再合并"的双表方案，偿还成本（859 行变更 + 迁移风险）远超一开始就单表的成本。建模发现两表职责重叠时要**尽快归一**，拖得越久适配层越厚。

### 4.4 问答来源遗漏：权限、元数据、SSE 顺序三合一修复（`597ccb0`）⭐

**问题**：用户提问后，回答里明明用了某文档的内容，参考列表里却没有它（来源遗漏）；普通用户能看到无权文档的下载链接；语音问答的 SSE 事件顺序不对导致前端渲染错乱。

**根因（多层叠加）**：
1. 四个检索通道（向量/关键词/标题兜底/图片）各自为政，授权过滤口径不一致；
2. 检索结果不带 `file_name`/`oss_key` 等元数据，引用构造时拿不到信息；
3. 关键词结果与向量结果合并时，同一文档的有效向量分块被错误丢弃；
4. 引用构造在授权过滤**之前**就生成 OSS 签名——越权 + 浪费签名计算；
5. 语音通道 `done` 事件先于 `references` 发出。

**解决**（一次性收口）：
- 统一资料库授权：超管全量（含私密）、其他角色各守范围，四通道统一调用；
- 移除默认"一年内"时间限制（历史上大量资料被这个隐藏默认值无声过滤）；
- 检索结果补齐 6 个元数据字段（source_type/source_url/file_name/oss_key/chunk_index/vector_id）；
- 引用构造重构：**先授权过滤，再生成签名**；`doc_id=0` 等非文件来源不再误查文档表；去除宽泛异常静默处理，下载链接失败打日志；
- 语音 SSE 顺序修复：`references` → `references_detail` → `done`；
- 索引任务重试前清理旧 Milvus 向量和 DocChunk，防重复索引。

**学到什么**：⭐ 多通道系统的三类典型事故——**口径不一**（权限/时间过滤各写各的）、**信息断链**（下游拿不到上游字段）、**顺序错乱**（流式协议事件序）。修复方式都是同一个：把散落逻辑收敛到唯一入口。另外"去除宽泛 except"是这次明确写进提交说明的原则——静默吞异常让问题延迟几个月才暴露。

## 五、稳定性建设（09-02 ~ 09-08）

### 5.1 大文件上传失败 → 分片传输（`62da072`）

**问题**：大文件（视频/大 PDF）整包上传，网络抖动即全部失败重来；nginx/代理层 body 大小限制进一步卡死大文件。

**解决**：`ChunkedUploadSession` 模型 + `chunked_views.py`（353 行）——初始化会话 → 逐片上传（可断点续传）→ 合并校验；Celery 任务清理超时未完成的会话防止垃圾堆积。

**学到什么**：上传问题的标准答案链是"客户端分片 → 服务端会话化 → 异步清理"，比调大 nginx body 限制治本。

### 5.2 提取层修复 + 索引可观测（`2d141fc`、`52f799b`）

**问题**：部分格式文件提取不到正文导致索引空转；索引失败时只有一句 status=failed，无法判断卡在下载、解析、分块还是 Embedding 哪一步。

**解决**：
- `2d141fc`：extractor.py +122 行，补格式支持与异常分支；
- `52f799b`：`KnowledgeDoc` 增加 `index_diagnostics` 诊断字段，索引任务各阶段写入结构化状态；建 `config/sqlite_test_backend/` 让测试环境可脱离 MySQL 跑。

**学到什么**：⭐ 异步管道（下载→解析→分块→Embedding→写向量库）每一步都要**留痕**。一个诊断字段让"索引失败"从玄学变成读一眼就知道卡在哪层。

### 5.3 环境兼容性（`68b6097`）

**问题**：审计表迁移里 `create_audit_tables` 是 MySQL 方言，SQLite 测试环境直接炸。

**解决**：迁移里加 `vendor != 'mysql'` 守卫；补知识库测试用例。

**学到什么**：写 MySQL 专属 SQL 的迁移必须考虑测试环境（SQLite）——守卫一行，CI 稳一半。

## 六、RAG 终局：多路召回与向量库 4 层根因（09-10）⭐⭐ 全项目最深的一次排查

### 6.1 检索通道缺失（`c36971b`，+369/-100）

**问题**：线上症状是"不管问什么，智能体给的参考文件永远是同样 5 篇"。排查发现检索层四个先天缺陷：
1. `file_name`（用户上传的原始文件名）从未参与检索——AI 改写过的 title 和用户记忆的文件名对不上；
2. `Keyword` 表 612 条标注数据从未被任何检索使用；
3. 兜底检索永远取文档**第一个**分块（答案在第 10 块也返回第 1 块）;
4. 没有正文检索通道——查询词只出现在正文时彻底搜不到。

**解决**：
- 统一基础件：`_extract_query_terms()`（停用词/中英混合拆解/jieba/同义词）、`_select_relevant_chunk()`（相关分块优先首块兜底）、`_build_doc_results()`（所有通道统一来源元数据）；
- 新增两路通道：`_keyword_table_search()`（Keyword 反查）、`_chunk_content_search()`（正文检索，先限定授权文档范围防越权）；
- 既有通道补 `file_name__icontains`；
- 合并逻辑两处修正：无向量命中时关键词分数**不再乘 0.3 衰减**（否则 0.55×0.3=0.15 被 min_score=0.30 全灭，新通道白建）；有正文命中时正文优先于标题摘录进 LLM 上下文；
- 配 9 个回归测试（含三层权限不绕过）。

**学到什么**：⭐ 给现有管道加通道，不要重写管道——旧 retrieve() 里的 Query 改写/Rerank/监控都是资产，新通道按既有接口插进去就行。"先测试复现问题，再动检索代码"，9 个测试保证了后续大改（b754139）不回归。

### 6.2 向量库 4 层根因（`b754139`）⭐⭐

多路召回上线后模拟检索暴露更深的真相：**向量通道命中数恒为 0**。逐层深挖出 4 层根因：

| 层 | 问题 | 证据 | 解决 |
|----|------|------|------|
| 1 | **向量库早已废弃**：3191 条向量中 3182 条是孤儿（对应文档已删），22 篇有效文档 17 篇无向量 | Chroma 与 MySQL 的 doc_id 对账 | 全量重建 |
| 2 | **删除不清理向量**：`delete_by_doc()` 在 Chroma 模式下是空操作（注释错误声称"不支持"），孤儿来源 | 215 个孤儿 doc_id 溯源 | 补真实 `delete(where=)`；删除视图接入 |
| 3 | **中文路径**：chroma-hnswlib 的 C++ 层打不开 `D:\实验室204\...`——写入进程正常，**重启后加载索引必崩**，这就是"索引显示成功、重启后向量全丢"的元凶 | ASCII 路径对照实验：同代码纯 ASCII 路径一切正常 | `CHROMA_DB_PATH` 迁至 `~/.campus_chroma_db` |
| 4 | **chromadb 版本叠加坑**：1.5.9 的 Rust hnsw 在 Windows 跨进程崩；0.6.3+hnswlib0.7.6 与 0.7.3 二进制互不兼容 | 版本组合矩阵逐一试错 | 固定 `chromadb==0.6.3 + chroma-hnswlib==0.7.3`；hnsw 崩溃自动降级 numpy 暴力余弦检索 |

**数据修复**：原计划走 index_document_task 重索引，撞上 OSS 403（AccessKey 无 GetObject 权限）且会把文档误标 failed——改从 MySQL `DocChunk.content` 直接批量 Embedding 重建，**绕过 OSS**，25 篇 5337 条向量与分块表完全对账。最终验证：向量命中 0 → 178/114，不同问题返回不同文档，测试 14/14。

**学到什么**（本项目最贵的 5 条教训）：
1. ⭐ **"索引成功" ≠ "向量可用"**——向量库写入必须用**跨进程重启后**的读取来验证，进程内一切正常可能是假象；
2. ⭐ **Windows + 中文路径是原生扩展（C/C++）的重灾区**——项目路径含中文时，数据文件一律放 ASCII 路径；
3. ⭐ **静默失败比崩溃更难查**——`delete_by_doc` 返回 True 的空操作、宽泛 except，让孤儿向量积累数月才爆发。修复时补了"hnsw 崩溃→暴力检索"的自动降级，宁要慢结果不要零结果；
4. ⭐ **向量库生态必须锁版本**——chromadb × chroma-hnswlib 的索引格式跨版本不兼容，requirements 精确锁定；
5. ⭐ **数据修复先看"账本"**——只要 MySQL DocChunk 完整，就能绕过外部依赖（OSS）从库内直接重建，不需要重新下载解析。

### 7.2 反复出现的问题模式（个人检查清单）

1. **静默失败**：空操作返回 True、宽泛 except、吞日志 → 排查成本指数上升（597ccb0、b754139 两次踩中）；
2. **口径不一**：权限/时间/过滤逻辑散落多处 → 收敛到唯一函数（`authorized_knowledge_docs()`、`context.py`、`http_client.py` 都是这么来的）；
3. **"看起来成功"**：索引任务返回成功 ≠ 数据可用；提交了 .pyc ≠ 该提交；需要"跨进程/重启后/对账式"验证；
4. **外部依赖不可控**：OSS 权限、IP 封锁、版本兼容、网关超时 → fallback 链 + 超时档案 + 锁版本；
5. **技术债拖延成本**：双表并存拖了两周才归一，代价 859 行；发现重叠尽快收敛。
