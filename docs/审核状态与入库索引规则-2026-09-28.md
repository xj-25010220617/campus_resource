# 审核状态、正式知识库存储与 RAG 索引的规则

> 生效日期：2026-09-28
> 对应迁移：`apps/knowledge/migrations/0011_unavailable_storage_allowed_drop_manual_confirmation.py`
> 可执行契约：`backend/apps/knowledge/tests/test_storage_vs_index_gate.py`

本文是这次规则变更的**唯一权威说明**。运维手册
（`docs/生产部署编排说明-2026-09-11.md`）第三章与
`scripts/reindex_all.bat` 的提示语都指向本文。

---

## 一、两条独立的判定

改造前的错误认知是把"审核通过"直接等同于"可以检索"。现在拆成两道门：

```
上传 → KnowledgeDoc 创建 → ContentModeration 创建
                                 ↓
                           审核（moderate_document）
                                 ↓
                    ┌── 存储门：is_storage_allowed(state) ──┐
                    │                                        │
                 允许                                      禁止
                    ↓                                        ↓
        正式知识库（OSS knowledge/ 前缀）              停在 quarantine/
        storage_state=promoted                        永不入库
                    ↓
        索引门：能不能解析出正文？
                    ↓
        解析成功 → 分块 → Embedding → 写入 Milvus → DocChunk
                    ↓
              status = 'indexed'
```

**关键结论**：

- **存储门**只看审核状态，不看文件类型、不看能不能解析。
- **索引门**在存储门之上，再要求"真的解析出正文、分块、Embedding、写入
  Milvus 全部成功"。
- `status='indexed'` 只在最后一步写入，全仓库**只有一个写入方**
  （`apps/knowledge/tasks.py` 的 `index_document_task`，在 Milvus 写入与
  `DocChunk.bulk_create` 之后）。

**「允许入库」≠「允许进入 RAG 索引」。**

## 二、状态放行表

| 审核状态 | 含义 | 进正式知识库 | 进 RAG 索引 |
| --- | --- | --- | --- |
| `approved` | 审核判定内容干净 | ✅ | ✅（若解析成功） |
| `unavailable` | 检测链没能给出结论（能力不足 / 服务不可用） | ✅ | ✅（若解析成功） |
| `rejected` | 已判定有害 | ❌ | ❌ |
| `pending` | 尚未审核 | ❌ | ❌ |
| `scanning` | 正在审核 | ❌ | ❌ |
| `error` | **审核过程发生异常** | ❌ | ❌ |

唯一判据是白名单常量 `STORAGE_ALLOWED_MODERATION_STATES`
（`apps/knowledge/moderation.py`）：

```python
STORAGE_ALLOWED_MODERATION_STATES = frozenset({approved, unavailable})
```

⚠️ **禁止改写成黑名单**（如 `state != 'rejected'`）。黑名单在将来新增状态时
会**静默放行**，白名单只会**静默拒绝**；同一个遗漏，后果完全相反。代码里有
`test_gate_matches_the_shared_whitelist` 与 `test_unknown_state_is_denied`
两条测试钉住这一点。

### `unavailable` 与 `error` 为什么必须区别对待

| | `unavailable` | `error` |
| --- | --- | --- |
| 语义 | 当前能力不足，**查不了** | 审核过程**本身出错了** |
| 内容是否可疑 | 未发现任何风险信号 | 未知 |
| 处理 | 自动入库 | 禁止入库，等重试 |

把两者混同，等于给"审核异常"开了一条放行路径。

## 三、`unavailable` 的完整行为

### 3.1 自动入库，不需要任何人工操作

`unavailable` 与 `approved` 在存储门上**同等放行**，由
`moderate_and_promote_task` 自动走 promotion →
`storage_state=promoted` → 派发 `index_document_task`。

**没有任何人工放行入口**：旧的 `confirmed_unchecked` 状态、
`apps/knowledge/confirmation.py`、`manage.py confirm_moderation`、
Admin 的"人工确认放行" action 与三个审计字段已随迁移 0011 一并删除。
Django Admin 里的内容安全审核页现在是**纯只读**的。

### 3.2 `unavailable` 是审核终态

`TERMINAL_MODERATION_STATES = {approved, rejected, unavailable}`。

它**不参与重试**（`retry_failed_moderations_task` 只挑 `state=error`）。
原因：`unavailable` 已经自动入库并可能已经发布；如果允许重审，一次迟到的
检测结果会把文档改成 `rejected`，留下"已发布但结论为拒绝"的内容，而系统
**没有降级/撤回流程**。与其造一个半成品撤回机制，不如让它停在终态。

**已知取舍**：ClamAV 等服务短暂故障期间上传的文件会被永久放行（未经检查）。
这是"检测链无结论即入库"这条业务规则的直接推论，不是实现缺陷。若要收紧，
需要的是"检测服务恢复后对 `unavailable` 存量重审 + 撤回"的完整设计，
而不是简单地把 `unavailable` 加回重试队列。

### 3.3 `unavailable` ≠ `approved`

两者在**存储**上同权，但在**审计语义**上必须始终可区分：
`unavailable` 表示"没查过"，`approved` 表示"查过且干净"。
任何把 `unavailable` 归一成 `approved` 的写法都会抹掉这个事实。

## 四、合法终态："已入库、未索引"

下面这条链是**预期行为**，不是故障：

```
unavailable → 允许入库 → 解析不出来（MP4 / ZIP / 无文字图片）
            → 有文件、不可搜索（status='failed'）
```

举例：一份 MP4 的审核结论是 `unavailable`。

1. 存储门放行 → 对象复制到 `knowledge/`，`storage_state=promoted`，
   `ContentModeration.state` **保持 `unavailable`**；
2. 索引门进入解析阶段 → 视频无法提取文本 → 解析为空；
3. `index_document_task` 判 `status='failed'` + `index_error`，
   **不**做分块、**不**调 Embedding、**不**写 Milvus、**不**写 DocChunk、
   **不**写 `status='indexed'`。

**绝不能为了让链路"看起来跑通"而伪造 `indexed`。** 那会让检索结果指向
不存在的向量，比"搜不到"严重得多。

对比：同样 `unavailable` 的一份 PDF，如果解析成功，就会正常走到
`indexed` 并可被检索。

## 五、运维怎么看

| 现象 | 原因 | 动作 |
| --- | --- | --- |
| 文档在正式区但搜不到 | 解析失败 / 无文本（如 MP4、ZIP、无文字图片） | 正常，看 `KnowledgeDoc.index_error` |
| 文档停在 `pending` / `scanning` | 审核未跑完 | 查 Celery worker 与 beat |
| 文档停在 `error` | 检测服务异常 | 查 `failure_reason`，先修服务；beat 会自动重试到上限 |
| 文档停在 `rejected` | 判定有害 | 无操作，不可翻案 |
| 想知道哪些文档没审核记录 | 历史存量（95 份） | 无审核记录 = 不进 RAG（fail-closed） |

查看入口：Django Admin → 内容安全审核（只读）。列表可按 `state` /
`storage_state` / `verdict` 筛选。**该后台没有任何写入能力。**

重索引：`scripts/reindex_all.bat`（先 `--dry-run`）。它逐份文档走
`check_indexable()`，没有任何批量删除/重置，`--force` 也不解除审核门。
